# Bounded local production-capacity check

Run `python scripts/production_capacity_check.py` from the canonical source worktree under WSL. The script binds a threaded Werkzeug HTTP server to loopback with an eight-request semaphore (a one-process/eight-slot approximation, not Gunicorn), writes to a disposable SQLite database under `/tmp/seatpal-production-capacity-20261016`, and stores the JSON report under `work/launch-capacity-20261016`. The database and run files are removed at exit; the report is retained. It seeds 100 synthetic member accounts, verifies the public phone-signup flow with an in-process OTP test provider, and uses a deterministic straight-line route fixture. It does not contact Railway, send SMS, use payment services, or call an external routing service.

The request phase ramps through 1, 5, 10, and 20 concurrent HTTP clients over `/`, `/api/bootstrap`, `/api/state`, and `/api/search`; it reports per-path p50/p95/p99 latency and statuses. It then sends requests from the synthetic users against a one-seat fixture ride and races the driver acceptance requests to check that exactly one seat wins and passenger state remains account-scoped. Finally, it snapshots and restores the isolated SQLite database with the existing backup helper and records database/WAL/SHM bytes and local recovery timings.

The built-in local-fixture gate is p95 below 2 seconds on each measured path, no unexpected HTTP errors, exactly one accepted seat with only expected 409 race losers, visible own-booking state and no cross-account booking state, and successful backup/restore. These are diagnostic thresholds for this local run, not evidence that the Railway deployment meets them. Use `--iterations` to increase samples and `--concurrency` to choose increasing levels; keep the default ceiling at 20 until results justify a change. The restore helper requires a filesystem that enforces owner-only POSIX permission bits. When that prerequisite is unavailable, the report marks recovery blocked and fails the full gate; run the harness from a POSIX filesystem to measure recovery. The harness does not represent 100 simultaneous users, Railway CPU or volume latency, network/TLS, third-party provider timing, human driver review, or a production recovery-point/recovery-time objective. OTP verification here proves route wiring only; it is not live signup-provider evidence.

Synthetic accounts receive signed test web sessions directly so the run can represent 100 users without exhausting the real per-IP login-attempt protection. Consequently, login throughput and credential checking are deliberately outside the measured capacity result. The signup probe does exercise `/api/phone/start`, `/api/phone/verify`, and profile completion over HTTP with the isolated provider.

Example from the canonical checkout in WSL (adjust the repository path if it is mounted elsewhere):

```sh
python scripts/production_capacity_check.py \
  --scratch-dir /tmp/seatpal-production-capacity-20261016 \
  --report-dir work/launch-capacity-20261016
```

## Latest local attempt

The 2026-10-16 WSL run reached the 20-client HTTP phase, one-seat acceptance race, and local backup/restore, but the overall result was **FAIL**: 3 `/api/state` requests returned 401 and 2 `/api/search` requests returned 403 at 20 clients. Diagnostics show each affected request had a valid signed cookie, matching synthetic account and CSRF token, but the cookie timestamp appeared 0.28–0.53 seconds in the future. That is consistent with Flask rejecting a timestamped session when wall-clock time moves behind its signed timestamp, but this run did not record the direct `max_age` exception. Timestamped Flask sessions are validated against wall-clock time, so run this harness only on a host with a stable wall clock. The one-seat race produced one accepted booking and 19 expected 409 responses; passenger state isolation and backup/restore passed. Treat the local concurrency/auth result as inconclusive. Do not weaken session or CSRF validation to make this fixture pass. Full diagnostics: `work/launch-capacity-20261016-cookie-diagnostic/production-capacity-20261016T063927Z.json`.
