# Phone signup release and activation

Public signup is for an adult passenger who needs their own account before arranging a shared seat. Provider-confirmed phone control creates or resumes a member account; it does not grant driver approval or verify legal identity. A new member must accept the current terms/privacy notice and adult attestation, then save a name before using travel features.

At the historical lifecycle/expense-budget milestone, the then-current candidate passed **600 backend tests**, with four optional local audio-decoder cases skipped because PyAV was unavailable. That count describes that source snapshot, not the current candidate or a fresh aggregate test run. Local browser evidence includes 14 lifecycle/budget groups, eight further groups after the individual-account collection guard, and three restart-continuity assertions. These are not unit-test counts. Native mounted checks, TypeScript and shared translations passed. The earlier phone-signup milestone's 481 backend passes and 13 browser groups, and the account-only milestone's 360 backend passes and 20 browser groups remain historical evidence. All SMS/account/document fixtures are synthetic: local checks do not establish real SMS delivery, the live MSG91 response contract, production activation or a new native release.

## Configuration

Only placeholder examples belong in `.env.example`. Configure actual values privately on the existing service after review.

| Variable | Required meaning |
| --- | --- |
| `APP_DISPLAY_NAME` | Current display label, `SeatPal`, used on the server-rendered public policy pages. This is not trademark clearance or a change to native identifiers/store metadata. |
| `PUBLIC_OPERATOR_NAME` | Actual accountable operator name; not a placeholder. |
| `PUBLIC_SUPPORT_EMAIL` | Actual monitored operator email with valid syntax. |
| `PHONE_AUTH_HMAC_KEY` | Stable high-entropy secret, at least 32 UTF-8 bytes. Preserve it across replicas, restarts and releases. The persistent fingerprint rejects an incompatible rotation; identity migration is required before changing it. |
| `PHONE_AUTH_DAILY_LIMIT` | Explicit integer from 1 to 100000, chosen for the approved SMS allowance. No unlimited or assumed free allowance. |
| `MSG91_WIDGET_ID` | Identifier for the account's active, six-digit SMS OTP widget. |
| `MSG91_TOKEN_AUTH` | MSG91 widget authentication value. The Web SDK receives it only after the user accepts consent and the server reserves a challenge; do not put it in logs or release evidence. |
| `MSG91_AUTH_KEY` | Server credential for access-token verification, kept server-side. |
| `MSG91_CONTRACT_VERIFIED` | Keep `0` until the real configured widget's exact send/verify/server-token-verification contract and failure behavior pass. Then set `1` only for that verified integration. |
| `PHONE_AUTH_ENABLED` | Defaults to `0`. This outer gate must be `1` before either MSG91 path is constructed. Set it only after the applicable activation gates below pass. Missing provider, key, limit or operator configuration keeps signup unavailable. |
| `PHONE_AUTH_SDK_ENABLED` | Defaults to `0`. Enables the browser-only Web SDK path when the SDK contract and provider abuse controls are confirmed. It does not enable native OTP, account recovery, or phone changes. |
| `MSG91_SDK_CONTRACT_VERIFIED` | Defaults to `0`. Set to `1` only after the configured Web SDK callback and server access-token verification contract have passed live checks. |
| `MSG91_PROVIDER_ABUSE_CONTROLS_CONFIRMED` | Defaults to `0`. Set to `1` only after provider-side CAPTCHA, rate limits, and abuse controls are confirmed for the configured widget. Application quotas alone do not cap provider SMS spend. |
| `DEMO_PASSWORD_ENABLED` | Defaults to `1` for existing password-protected development identities and staff access. Keep separate from public phone signup; never migrate or expose demo/staff credentials as customer accounts. |

`DIRECT_UPI_ENABLED` is independent and still defaults off. Enabling phone signup does not authorize collections or a paid SMS purchase. Existing production configuration is unchanged by this source work.

### One-shot native REST adapter diagnostic

From the repository root in a trusted server shell where the four required variables are already present in the process environment, `python -m scripts.verify_msg91_contract` reports only whether each value is present and well formed. It performs no network request. After the account, operator and test-number owner have authorized one SMS, `python -m scripts.verify_msg91_contract --send-test` prompts for the `+91` test phone and six-digit code using hidden terminal input. It sends exactly once and verifies exactly once through the existing native REST adapter; it has no resend, retry, or wrong-code probe. If hidden input cannot disable echo, it aborts. Do not pass private values as command-line arguments, echo or export them in terminal commands, dump the environment, or copy phone/code/provider output into chat or logs. Run only in an interactive trusted shell with credentials supplied by the deployment environment.

The live probe checks the adapter's send/request-id, request-bound OTP verification and server access-token verification path. It does not create an application account, exercise server challenge/rate-limit behavior, establish negative/failure contracts, verify the separate browser Web SDK, or by itself justify production readiness. `MSG91_CONTRACT_VERIFIED` remains off until the broader native REST contract and failure behavior are reviewed; Web SDK gates remain separate.

The Web SDK is the current browser signup/sign-in integration: its widget sends the OTP and returns an opaque token, which the server verifies with MSG91 before creating or resuming the member account. `MSG91_TOKEN_AUTH` is exposed to the browser only after a consented challenge is reserved; `MSG91_AUTH_KEY` remains server-side. Native sign-in, account recovery, and phone changes use the separate legacy REST OTP integration and require `MSG91_CONTRACT_VERIFIED=1`. Enabling the Web SDK alone does not enable those flows.

The private operator snapshot and non-overwriting restore commands are documented in [backup-restore.md](backup-restore.md). They preserve the database's phone-key binding but never export the external key. A successful local drill does not establish that hosted or off-host backups are active.

## MSG91 Web SDK status (2026-10-16)

The optional Web SDK path is separate from legacy server-side REST OTP. It is browser-only; native sign-in, recovery, and phone changes continue to require the legacy provider path. The server reserves and rate-limits a local five-minute challenge, then verifies the SDK's opaque access token with MSG91 and matches the provider-returned mobile identifier to that challenge. MSG91's widget token proves a verified identifier, not a particular server-reserved send. The current integration uses the provider's default widget UI with `exposeMethods: false`; custom global methods are excluded because they are non-configurable closures bound to the first widget instance, so reinitializing them can break resend behavior. The provider UI owns CAPTCHA, OTP entry, and retries. Its resend may not create a new server-side local challenge; application counters therefore do not meter each provider resend, and provider-side send limits and CAPTCHA are required. The widget has a minimum 15-minute provider expiry; local expiry remains five minutes.

All SDK gates default off: `PHONE_AUTH_ENABLED`, `PHONE_AUTH_SDK_ENABLED`, `MSG91_SDK_CONTRACT_VERIFIED`, and `MSG91_PROVIDER_ABUSE_CONTROLS_CONFIRMED`. The SDK additionally requires the stable identity key, explicit daily cap, configured widget values, and real operator/support details. The client receives its public widget token only after a consented, same-origin challenge is reserved; the server credential is never sent to the browser. Since a public widget token can be used directly outside the app, server quotas cannot guarantee an SMS-spend ceiling. Provider-side limits, CAPTCHA, and abuse controls must be confirmed before enabling the path; do not claim a hard cost cap from application counters.

An earlier MSG91 account observation showed KYC required and a blank Digio verification overlay. The October 16 check confirmed the widget is Active/Enabled and the wallet balance is ₹0; it did not verify current KYC status or whether the default subscription requires funding. The current provider credential blocker is owner-mobile verification before the existing Authkey can be retrieved; no phone number has been entered. Eleven settings changes are staged and none have been deployed; all signup and contract-verification flags remain `0`. No real SMS was sent and no application account was created. The saved widget is India-only, six digits, with CAPTCHA enabled, Invisible OTP disabled, and a 60-second resend setting; its default template branding still needs review. The supplied brand is Seatpal.in; no corporation has been verified. Provider abuse controls, the live widget callback and server-verification contract, and an authorized real-number delivery test remain pending.

## Activation gates

1. Complete the current phone backend/HTTP, web and native freeze; create a new manifest and archive. Do not deploy the older account-flow milestone as the completed phone-signup release. Both packaging scripts require `app/templates/public-policy.html`; Docker's existing `COPY app/` includes it.
2. Configure the actual MSG91 widget for six-digit SMS delivery. With explicit provider/account authorization, check real delivery, the widget callback, and server access-token verification against the expected identifier. Check wrong/expired codes, provider-owned resend behavior, and provider failures. The SDK token does not prove a particular server-reserved send or request ID. Documentation-shaped fixtures do not establish the live account contract; do not bypass `MSG91_SDK_CONTRACT_VERIFIED` or `MSG91_PROVIDER_ABUSE_CONTROLS_CONFIRMED` to make the UI appear enabled.
3. Supply the real operator/support details and review the public `/terms` and `/privacy` pages, including consent versions and current data/retention statements. Configure the stable secret and an approved bounded daily allowance. Do not print provider responses, credentials, codes or phone numbers in release evidence.
4. After the new release is authorized and deployed, inspect `/api/phone/capabilities` and bootstrap: signup must remain unavailable until deliberately enabled and fully configured. Verify the normal Indian-phone (+91) flow, separate browser/mobile sessions, logout, incomplete-profile restriction and returning-account behavior using authorized test numbers. Phone ownership alone must never produce driver/staff approval.
5. Verify the exact installed native build, device and backend configuration, then test the real phone flow on that build before claiming TestFlight readiness. No current source or package operation sends SMS, deploys, commits or uploads by itself.

Public endpoints are `GET /api/phone/capabilities`, browser `POST /api/phone/{start,resend,verify}`, mobile `POST /api/mobile/phone/{start,resend,verify}`, and authenticated `POST /api/phone/profile`. Policy pages are available without sign-in. The implemented deletion and saved-code phone-recovery endpoints are specified in [account-lifecycle-contract.md](account-lifecycle-contract.md), including fresh purpose/session-bound proof, travel/payment blockers and disclosed retention. They need their own release verification; they do not provide recovery without a saved code or protection against recycled-number OTP sign-in. Staffed support, external retention and approved operating/payment policy remain launch requirements.
