# Driver evidence storage

Driver licence, RC, insurance and selfie BLOBs use Fernet authenticated encryption with the configured `IDENTITY_EVIDENCE_KEY`. The key is shared with identity evidence but has a separate persistent `driver_encryption_config` guard. Keep that key outside the database in secret storage, retain it through restart and restore, and never put it in source control or command arguments. No key is generated by the service.

## Boundaries

New BLOBs have `encoding=1`; pre-encryption rows have `encoding=0`. Startup may add the encoding column and key guard but never encrypts legacy rows automatically. Missing, malformed or mismatched keys disable new uploads, owner reads, reviewer previews, submission and approval with a bounded 503. Missing or corrupt BLOBs and unknown encodings also fail closed. Every required BLOB must decrypt and match its recorded size, digest and media type before submission or approval.

Authenticated status, rejection, revocation, consent withdrawal and retention cleanup remain available without a working key. Existing approval chronology and trip/payment eligibility are not changed merely because storage needs conversion; a human review and encryption configuration are different facts. Do not enable public OTP, document intake or direct UPI until the storage check below passes.

Only currently authorized owners may read originals. Staff receive flattened, watermarked previews after capability, consent and application checks. Authorization, version and the stored ciphertext digest/encoding are checked again after rendering, before pixels or an inspection receipt are returned. This does not prevent screenshots or make a document authentic.

Only BLOB content is encrypted. Application names, vehicle details, filenames, document metadata, expiry dates, hashes, staff reasons and review records remain in the private SQLite store. Full-disk/volume protection, access control, protected backups and key recovery remain operator responsibilities. Logical deletion or conversion does not securely erase old database pages, SQLite WAL files or backups.

## Read only readiness check

Use the deployment's Python environment with its declared dependencies. Supply the existing key through secret environment injection, not a literal shell argument:

```bash
python -m app.driver_verification --database /absolute/path/store.sqlite3 --check
```

The command only reports aggregate legacy, encrypted and invalid-encoding counts plus `ready`. Exit 0 means every driver BLOB has valid Fernet storage and matching metadata, the driver guard is present and valid, and any existing identity guard accepts the same key. Exit 1 means not ready, including missing blobs, missing guards, legacy storage or undecryptable ciphertext. An empty newly initialized store still needs its valid driver guard. No evidence, document IDs or key material is printed.

## Explicit offline legacy conversion

1. Keep public intake and new direct-UPI collection disabled. Stop every application and worker accessing the database. `--offline` is an operator assertion, not automatic proof that processes are stopped.
2. Take a protected, consistent backup including all SQLite tables. Confirm the recovery key and a restore procedure; never replace a mismatched or missing guard to force conversion.
3. Rehearse on an isolated restored copy. Supply the same existing key used by identity evidence, then run:

```bash
python -m app.driver_verification --database /absolute/path/offline-copy.sqlite3 --offline
python -m app.driver_verification --database /absolute/path/offline-copy.sqlite3 --check
```

Conversion validates the existing driver and identity guards before changing evidence. With no driver guard, it can create one only when no encrypted/unknown-encoding rows already exist. It validates all BLOBs against their metadata, encrypts only legacy rows, and preserves IDs, document metadata, application versions and approval records. Schema, guard and BLOB writes are one transaction: any failure rolls them all back. Running it again on a clean store converts zero rows. This is not key rotation.

4. Only after rehearsal and backup verification, repeat on the stopped deployment database and require `--check` to pass before restarting. Follow the separate beta release approval; this command does not enable any feature flag.
5. Handle old plaintext backups, database pages and WAL retention under the operator's retention policy. This procedure does not claim physical secure erasure.

No live database conversion is performed as part of implementing this feature. Tests use temporary synthetic databases and ephemeral keys.
